# 架构设计

## 1. 定位

一个**编排层**，不是又一个测试框架。

现有的 AI 测试工具（midscene / Playwright / Appium / browser-use）解决的是「**怎么操作界面**」；本平台解决的是「**谁来决策、谁来判断、谁来闭环**」：

```
代码提交  →  构建  →  部署到设备  →  设计测什么  →  执行  →  判定对错  →  出报告  →  建 bug  →  确认
             ↑ 复用 CI        ↑ 复用烧录工具        ↑ ★ 自研        ↑ 复用执行器   ↑ ★ 自研          ↑ ★ 自研
```

★ 标记的三处（测试设计、判定归因、缺陷闭环）是差异化价值所在，其余全部复用成熟组件。

## 2. 为什么不自研执行器

调研结论（2026-11 数据）：

| 能力 | 现成方案 | 我们怎么做 |
|---|---|---|
| Web UI 操作 | Playwright（事实标准） | 直接调用 |
| Android 操作 | ADB + Appium | 直接调用 |
| 视觉定位（看图点按钮） | midscene（15.5k★，中国团队，原生支持 Qwen-VL） | 作为可选执行器接入 |
| 通用 Agent 框架 | browser-use（120k★） | 不引入，过重 |
| 烧录/串口 | esptool / openocd / pyserial | 包一层 `SerialDevice` |

自研执行器 = 重复造轮子且必然打不过社区。**平台的护城河在决策质量，不在点击精度。**

## 3. 分层与数据契约

每层输入输出都是 JSON，落在 `runs/<run_id>/` 下，可单独重放、单独替换。

```
┌─────────────────────────────────────────────────────────────┐
│ 生成   product.json    {name, path, files[], generator,      │  ← DeepSeek 写代码
│                        contract{ok, summary, missing[]}}     │
├─────────────────────────────────────────────────────────────┤
│ 触发   event.json      {repo, commit, branch, changed_files} │
├─────────────────────────────────────────────────────────────┤
│ 构建   build.json      {kind, path, sha256, files[]}         │
├─────────────────────────────────────────────────────────────┤
│ 部署   deploy.json     {device, artifact, method, work_dir}  │
├─────────────────────────────────────────────────────────────┤
│ 设计   testplan.json   {rationale, cases[]}                  │  ← DeepSeek
├─────────────────────────────────────────────────────────────┤
│ 执行   traces.json     [{case_id, steps, screenshot, logs,   │
│                         state{screen,online,version,ok},     │
│                         contract_ok, skipped}]               │
├─────────────────────────────────────────────────────────────┤
│ 判定   verdicts.json   [{case_id, verdict, judged_by,        │  ← 规则 / 状态 / 视觉
│                         evidence_key, rca}]                  │
├─────────────────────────────────────────────────────────────┤
│ 报告   report.md/.json {total, passed, failed, inconclusive,  │
│                         skipped, pass_rate, usage}           │
├─────────────────────────────────────────────────────────────┤
│ 建单   bugs.json       [{id, title, fingerprint, status}]    │
├─────────────────────────────────────────────────────────────┤
│ 确认   confirmation.json                                      │
└─────────────────────────────────────────────────────────────┘
```

### 第 0 层：AI 生成产品代码（可选）

`aqa demo` 时启用。这是「AI 原生」最激进的部分 —— **被测对象本身也由 AI 生成**：

- 输入：一句自然语言需求
- 第一步：只让模型出文件清单（≤8 个文件）
- 第二步：逐文件生成，`main.py` 先跑，其余 3 并发；每个文件独立调用
- 校验：实跑一次 `main.py boot`，检查是否输出符合契约的 `STATE`
- 修复：不合规就把违规点（缺哪个字段、退出码、stdout 尾部）喂回模型改一轮
- 降级：仍不可用则回落到内置模板，降级事实写入 `product.json` 的 `generator`

**为什么不用一次性生成整棵树**：一次吐 8 个文件必然撞 `max_tokens`，返回的是残 JSON，
整轮白跑。拆成「清单 + 逐文件」后单次输出可控，失败也只影响单个文件。

代价：一个 8 文件项目约 8 次调用、5~10 万 token（≈0.2~0.3 元）、1~2 分钟。

这样做的好处是：需求变更后能立刻生成新版本并回归，形成「改需求 → 自动生成 → 自动测」的紧闭环。
风险也明显 —— **AI 写的代码不能直接上生产**，所以这一层默认关闭，且生成物必须先过测试链路。

### 第 0.5 层：设备状态契约（`contract.py`）

AI 写代码时字段命名是自由的：`fw_version` / `cloud.connected` / `result` 都可能出现。
如果判定层按写死的键名去读，就会把「字段名不一样」判成「设备故障」——
实测中这一层缺失导致一轮产出 4 条假 bug。

契约做三件事：

1. **归一化**：别名表把任意合理命名映射成 `screen / online / version / ok`，
   值做类型强转（`"true"` → `True`，`1.4` → `"1.4"`），并记录每个字段实际来自哪个键
2. **自检**：生成后立即实跑，不通过就带着「契约不通过」标记继续跑，而不是假装没事
3. **修复**：把违规点喂回模型改一轮（只改需要的文件）

`judge_by_state` 只在 `is_usable(state)` 为真时才工作 —— 读不到就交给视觉，
绝不拿「读不到」当「坏了」。

## 4. 模型分工

默认**一个 DeepSeek Key 打通全流程**（实测 `deepseek-flash` 支持图像输入）：

| 环节 | 需要什么能力 | 默认选型 | 可替换 |
|---|---|---|---|
| 生成产品代码 | 长输出、代码结构一致性 | deepseek-flash（32K 预算） | 任何 OpenAI 兼容端点 |
| 设计测试用例 | 读 diff、理解业务意图、推理风险面 | deepseek-flash | — |
| 判定与归因 | 从「状态 + 日志 + 截图」推结论 | 规则/状态优先，视觉兜底 | Qwen-VL / 本地 VLM |
| 写 bug 报告 | 结构化表达、复现步骤 | deepseek-flash | — |

**推理模型的预算分档**（踩过的坑）：`deepseek-flash` 先思考再输出，
8K 预算会被思考吃光导致 `content` 为空。所以：

| 用途 | 变量 | 默认 |
|---|---|---|
| 写代码 | `AQA_MAX_TOKENS_GEN` | 32768 |
| 设计/归因/写单 | `AQA_MAX_TOKENS` | 8192 |
| 视觉 | `AQA_MAX_TOKENS_VISION` | 2048 |

单文件生成被截断时预算自动翻倍重试一次；仍失败则只丢这个文件，不整轮降级。

**部署形态三选一**：
1. 公有云 API（最快起步，¥0.3~0.5/run 含代码生成）
2. vLLM 自建（一张 4090 可跑 Qwen2.5-VL-7B + DeepSeek-R1-14B 量化）
3. Ollama（单人开发最省事，`ollama pull qwen2.5vl:7b`）

> 注意：本机（i7-8550U / 8G 内存 / MX150 2G）跑不动本地大模型。

## 5. 嵌入式场景的特殊设计

这是与 Web 测试框架最大的不同，四条硬约束：

1. **部署 = 烧录**：不是发 URL，而是写 flash / install apk。`deploy()` 收 artifact 与目标设备，失败必须能回滚（保留上一版固件）。
2. **没有 DOM**：状态只能从「屏幕像素 + 串口日志 + 云端上报」三处推断，所以 `Trace` 同时携带三者。
3. **设备会挂**：串口死锁、看门狗重启、USB 掉线。每个用例执行必须有超时；失败不等于 bug，也可能是环境问题 —— 所以判定层要能区分「设备异常」与「功能缺陷」。
4. **断电/断网是常态**：OTA、配网这类用例本身就在测异常恢复，测试环境要能主动制造断网（docker network / iptables / 继电器）。

## 6. 失败语义

| 阶段失败 | 处理 | 理由 |
|---|---|---|
| 触发 / 构建 | 立即中止，报错退出 | 产物都没有，测了无意义 |
| 部署 | 重试 2 次（幂等烧录），仍失败则中止 | 烧录失败多为硬件/线缆问题，重试常能过 |
| 设计 | 重试 1 次，仍失败用规则兜底（冒烟用例集） | 模型偶发返回非 JSON，不该阻塞质量门禁 |
| 执行（单用例） | 不中断整轮，标记该用例异常 | 一个用例挂不能影响其余用例结论 |
| 判定 | 视觉异常先重试一次；仍失败按 FAIL 且置信度 0 | 单次网络抖动不该翻转结论 |
| 判定结论 | `INCONCLUSIVE`（状态读不到）/ `SKIPPED`（设备不支持） | 这两类不建缺陷：**误报比漏报更贵**，会污染缺陷库 |
| 建单 | 失败则本地留存草稿，不阻塞流程 | 缺陷系统挂了不该让整轮白跑 |

## 7. 缺陷去重（已实现）

同一个故障会命中多个用例（配网缺陷同时导致「不上线」和「超时重试」）。按用例去重会污染缺陷库。

**先试过按根因文本去重，失败了**：7 个用例对应 2 个故障，但模型给每个用例写的
`root_cause` 措辞都不同 → 指纹不同 → 建了 7 条 issue。

最终方案：`fingerprint = sha1(evidence_key)`，证据键由判定层产出，与措辞无关：

| 判定路径 | 证据键示例 |
|---|---|
| 日志硬信号 | `rule:system_reset:provision` |
| 状态不符预期 | `state:provision:online` |
| 视觉判定 | 回退到根因文本（无稳定现象键时） |

- 命中已有证据键 → 不新建 issue，只把用例追加到 `affected_cases`；**且跳过写 bug 的模型调用**
- `bugs.json` 只存唯一缺陷（带 `created_this_run`），不再把同一对象按用例重复列一遍

已知局限：同一根因若同时触发两条路径（先 system_reset 再 offline），会得到两个证据键、
两条 issue，需要人工合并。放宽到「同场景合并」会掩盖不同缺陷，暂不采用。

## 8. 成本模型（实测）

真模型完整跑一轮（生成 8 文件产品 + 7~11 个用例）：

| 项 | 用量 | 成本 |
|---|---|---|
| 生成产品代码 | 8 次调用，5~10 万 token | ≈ ¥0.25 |
| 测试设计 | 1 次，~1.5 万 token（含思考） | ≈ ¥0.03 |
| 判定 | 规则/状态短路，多数用例 0 次模型调用 | ≈ ¥0.02 |
| 归因 + 写 bug | 仅失败用例 | ≈ ¥0.10 |
| **合计** | 10~18 次调用 / 10~12 万 token | **≈ ¥0.3~0.5 / run** |

纯回归（不生成产品，`aqa run`）只需判定与归因，约 ¥0.05 / run。
按每天 50 次提交算：≈ ¥2.5/天。报告里的 `usage` 字段是真实计费数据，不是估算。

## 9. 演进路线

**P0（已完成）**：十层骨架 + mock 闭环 + 适配器抽象 + 状态契约 + 三级判定 ✅

**P1 可用**：
- 接真实设备（ADB / 串口）
- 视觉定位：把「点哪里」交给 VLM，取代脚本硬编码坐标
- 用例库沉淀：通过的用例自动转回归集，下次先跑回归

**P2 好用**：
- 设备农场：多设备并行、抢占调度、失败自动隔离
- 失败聚类：把相似根因的失败合并，减少噪声
- 质量门禁：通过率低于阈值自动阻断合并

**P3 智能**：
- 变更影响分析：只测受影响的模块，把 30 分钟全量回归压到 3 分钟
- 自愈：定位失败时自动尝试备选路径（换选择器 / 重试）
