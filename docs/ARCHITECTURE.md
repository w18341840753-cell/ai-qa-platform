# 架构设计

## 1. 定位

一个**编排层**，不是又一个测试框架。

现有的 AI 测试工具（midscene / Playwright / Appium / browser-use）解决的是「**怎么操作界面**」；本平台解决的是「**谁来决策、谁来判断、谁来闭环**」：

```
代码提交  →  构建  →  部署到设备  →  设计测什么  →  执行  →  判定对错  →  出报告  →  建 bug  →  确认
             ↑ 复用 CI        ↑ 复用烧录工具        ↑ ★ 自研        ↑ 复用执行器   ↑ ★ 自研          ↑ ★ 自研
```

★ 标记的三处（测试设计、判定归因、缺陷闭环）是差异化价值所在，其余全部复用成熟组件。

## 2. 为什么不自研执行器

调研结论（2026-11 数据）：

| 能力 | 现成方案 | 我们怎么做 |
|---|---|---|
| Web UI 操作 | Playwright（事实标准） | 直接调用 |
| Android 操作 | ADB + Appium | 直接调用 |
| 视觉定位（看图点按钮） | midscene（15.5k★，中国团队，原生支持 Qwen-VL） | 作为可选执行器接入 |
| 通用 Agent 框架 | browser-use（120k★） | 不引入，过重 |
| 烧录/串口 | esptool / openocd / pyserial | 包一层 `SerialDevice` |

自研执行器 = 重复造轮子且必然打不过社区。**平台的护城河在决策质量，不在点击精度。**

## 3. 分层与数据契约

每层输入输出都是 JSON，落在 `runs/<run_id>/` 下，可单独重放、单独替换。

```
┌─────────────────────────────────────────────────────────────┐
│ 生成   product.json    {name, path, files[], generator}      │  ← DeepSeek 写代码
├─────────────────────────────────────────────────────────────┤
│ 触发   event.json      {repo, commit, branch, changed_files} │
├─────────────────────────────────────────────────────────────┤
│ 构建   build.json      {kind, path, sha256, files[]}         │
├─────────────────────────────────────────────────────────────┤
│ 部署   deploy.json     {device, artifact, method, work_dir}  │
├─────────────────────────────────────────────────────────────┤
│ 设计   testplan.json   {rationale, cases[]}                  │  ← DeepSeek
├─────────────────────────────────────────────────────────────┤
│ 执行   traces.json     [{case_id, steps, screenshot, logs}]  │
├─────────────────────────────────────────────────────────────┤
│ 判定   verdicts.json   [{case_id, verdict, confidence, rca}] │  ← Qwen-VL + DeepSeek
├─────────────────────────────────────────────────────────────┤
│ 报告   report.md/.json {total, passed, failed, pass_rate}    │
├─────────────────────────────────────────────────────────────┤
│ 建单   bugs.json       [{id, title, fingerprint, status}]    │
├─────────────────────────────────────────────────────────────┤
│ 确认   confirmation.json                                      │
└─────────────────────────────────────────────────────────────┘
```

### 第 0 层：AI 生成产品代码（可选）

`aqa demo` 时启用。这是「AI 原生」最激进的部分 —— **被测对象本身也由 AI 生成**：

- 输入：一句自然语言需求
- 输出：一个可运行的项目（入口脚本 + 设备状态机 + 串口日志协议）
- 校验：必须存在 `main.py`，必须支持按场景驱动，必须输出 `STATE {json}`
- 降级：模型产出不可用时自动回落到内置模板，但降级事实写入 `product.json` 的 `generator` 字段

这样做的好处是：需求变更后能立刻生成新版本并回归，形成「改需求 → 自动生成 → 自动测」的紧闭环。
风险也明显 —— **AI 写的代码不能直接上生产**，所以这一层默认关闭，且生成物必须先过测试链路。

## 4. 模型分工（关键决策）

**不能用单一模型打通全流程**，原因是能力不匹配：

| 环节 | 需要什么能力 | 选型 | 理由 |
|---|---|---|---|
| 设计测试用例 | 读代码 diff、理解业务意图、推理风险面 | **DeepSeek-V3**（文本） | 中文语境强、代码理解好、API 便宜（约 ¥1/百万 token） |
| 执行中的视觉定位 | 看图找元素、判断界面状态 | **Qwen2.5-VL / Qwen3-VL**（视觉） | DeepSeek 无视觉能力；Qwen-VL 开源可私有化，midscene 原生适配 |
| 判定与归因 | 关联「截图异常 + 串口日志」推理根因 | 两者协作：VLM 判现象，文本模型做因果 | 单纯 VLM 归因易幻觉，纯文本又看不到图 |
| 写 bug 报告 | 结构化表达、复现步骤 | DeepSeek-V3 | 模板化输出稳定 |

**部署形态三选一**：
1. 公有云 API（最快起步，¥0.01~0.05/run）
2. vLLM 自建（一张 4090 可跑 Qwen2.5-VL-7B + DeepSeek-R1-14B 量化）
3. Ollama（单人开发最省事，`ollama pull qwen2.5vl:7b`）

> 注意：本机（i7-8550U / 8G 内存 / MX150 2G）跑不动本地大模型，硬件清单见 README 讨论记录。

## 5. 嵌入式场景的特殊设计

这是与 Web 测试框架最大的不同，四条硬约束：

1. **部署 = 烧录**：不是发 URL，而是写 flash / install apk。`deploy()` 收 artifact 与目标设备，失败必须能回滚（保留上一版固件）。
2. **没有 DOM**：状态只能从「屏幕像素 + 串口日志 + 云端上报」三处推断，所以 `Trace` 同时携带三者。
3. **设备会挂**：串口死锁、看门狗重启、USB 掉线。每个用例执行必须有超时；失败不等于 bug，也可能是环境问题 —— 所以判定层要能区分「设备异常」与「功能缺陷」。
4. **断电/断网是常态**：OTA、配网这类用例本身就在测异常恢复，测试环境要能主动制造断网（docker network / iptables / 继电器）。

## 6. 失败语义

| 阶段失败 | 处理 | 理由 |
|---|---|---|
| 触发 / 构建 | 立即中止，报错退出 | 产物都没有，测了无意义 |
| 部署 | 重试 2 次（幂等烧录），仍失败则中止 | 烧录失败多为硬件/线缆问题，重试常能过 |
| 设计 | 重试 1 次，仍失败用规则兜底（冒烟用例集） | 模型偶发返回非 JSON，不该阻塞质量门禁 |
| 执行（单用例） | 不中断整轮，标记该用例异常 | 一个用例挂不能影响其余用例结论 |
| 判定 | 异常按 FAIL 处理并标注低置信度 | **宁可误报，不可漏报** |
| 建单 | 失败则本地留存草稿，不阻塞流程 | 缺陷系统挂了不该让整轮白跑 |

## 7. 缺陷去重（已实现）

同一个根因会命中多个用例（配网缺陷同时导致「不上线」和「超时重试」）。按用例去重会污染缺陷库。

方案：`fingerprint = sha1(normalize(root_cause))`，跨 run 持久化在 `.aqa/bugs.json`。
- 命中已有指纹 → 不新建 issue，只把用例 ID 追加到 `affected_cases`（用于统计影响面）
- 这也天然实现了「同一 bug 在多个版本的回归中只报一次」

## 8. 成本模型（估算，单 run）

| 项 | 用量 | 成本 |
|---|---|---|
| 测试设计 | 1 次调用，~2K token 输入 / 1K 输出 | ≈ ¥0.02 |
| 视觉判定 | 4 用例 × 1 张截图 | ≈ ¥0.04 |
| 归因 | 仅失败用例，2 次 | ≈ ¥0.02 |
| 写 bug | 仅失败用例，2 次 | ≈ ¥0.02 |
| **合计** | | **≈ ¥0.1 / run** |

按每天 50 次提交算：约 ¥5/天。这是 API 方案的核心优势。

## 9. 演进路线

**P0（当前）**：九层骨架 + mock 闭环 + 适配器抽象 ✅

**P1 可用**：
- 接真实设备（ADB / 串口）
- 视觉定位：把「点哪里」交给 VLM，取代脚本硬编码坐标
- 用例库沉淀：通过的用例自动转回归集，下次先跑回归

**P2 好用**：
- 设备农场：多设备并行、抢占调度、失败自动隔离
- 失败聚类：把相似根因的失败合并，减少噪声
- 质量门禁：通过率低于阈值自动阻断合并

**P3 智能**：
- 变更影响分析：只测受影响的模块，把 30 分钟全量回归压到 3 分钟
- 自愈：定位失败时自动尝试备选路径（换选择器 / 重试）
