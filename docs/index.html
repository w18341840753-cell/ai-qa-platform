## 概要

## 复现步骤

1. 擦除/清空 NVS 中的配网信息（无 SSID、无配网标志）。
2. 断开 wifi、cloud 处于 offline。
3. 设备冷启动，观察 `[ui]` 输出的 screen 状态与 `STATE` 报文。

## 实际结果

```

```

- 在 `wifi state=disconnected`、`cloud state=offline` 的情况下，启动序列中未触发任何 provision 状态迁移。

## 预期结果

```
screen=provision
```

冷启动未配网时应进入配网引导状态并完成自检。

## 根因分析

UI 启动状态机的初始屏幕被硬编码/默认置为 `home`，缺少「未配网则进入配网引导」的判断分支。配网入口逻辑（判断 NVS 中是否存有 SSID/配网标志位 → 跳转 provision）在启动序列中被遗漏，或条件判断恒为 false，可能的成因包括：

- `provisioned` 标志默认初始化为 `true`；
- 配网状态读取早于 NVS 初始化完成，返回默认值。

## 建议修复

1. 在 UI 启动阶段（wifi/net 模块就绪后）增加显式路由：读取持久化的配网标志与 SSID，若未配网或 wifi 未连接则强制 `screen=provision`，并打印 `[prov] enter reason=...` 便于回归定位。
2. 检查 `provisioned` 标志的默认值与 NVS 初始化时序，避免读取早于存储就绪。
3. 为该分支补充启动自检断言与用例覆盖（冷启动未配网 → provision；已配网 → home）。
4. 在 `STATE` 报文中输出 `provisioned` 字段以便自动化判定。

## 影响

未配网设备冷启动后停留在 home 界面，用户无法进入配网流程，设备不可用；自动化用例 TC-01 及相关启动自检持续失败。

## 概要

执行用例 **TC-05 OTA 镜像校验失败不写入分区** 时断言失败：期望 `STATE.ok == False`，实际 `STATE.ok == True`。

## 复现信息

- 用例：TC-05 OTA 镜像校验失败不写入分区
- 触发方式：auto（CI 自动执行）
- 期望：`STATE.ok == False`（verify 失败、升级中止、slot=b 未被写入）
- 实际：`STATE.ok == True`（升级成功完成）

## 关键日志

```
manifest 下发 -> download 100%
verify signature=ok crc32=ok target_slot=b
install slot=b ... ota_done
STATE.ok=True
```

manifest 声明的镜像属性为 `crc32=0x8a41f3c2` 且携带签名；日志显示校验结果 `signature=ok crc32=ok`，说明下发的镜像与 manifest 一致，固件无任何理由判定失败，故上报 `ok=True` 属预期行为。

## 根因分析

**主因（测试桩/注入手段）**

1. OTA mock 或服务端下发的镜像未被篡改；或篡改镜像后同步更新了 manifest 中的 `crc32` / `signature`，导致期望的“校验失败”场景实际不存在。
2. 用例未对“verify 失败分支”日志（fail + abort 关键字）做断言，无法在注入失效时快速区分“注入没生效”与“固件没拦住”。

**次要疑点（待后续验证，非本次定因）**

3. 日志中 verify 结果仅一行 `signature=ok crc32=ok` 后即进入 install，缺少 verify 失败分支的 abort 日志，也无“写入前阻断”的直接证据。若后续注入生效后仍出现 `install`，则需怀疑校验结果仅被记录而未真正门控写入（verify 与 erase/write 的执行顺序问题）。

## 修复建议

1. **修复故障注入**：让 OTA mock 下发与 manifest 不一致的镜像，例如翻转首字节、截断至 `<size`、返回错误 crc32，或使用与 manifest 公钥不匹配的签名，确保 verify 必然失败；用例中断言日志必须出现 `verify fail` 与 `abort` 关键字。
2. **固件侧增强可观测性与门控**：verify 失败必须打印 `[ota] verify fail reason=signature|crc32 abort` 并直接 `return`，禁止进入 erase/write；`install` 置于 verify 成功分支之后；slot=b 写入前增加分区写保护/长度上限检查。
3. **STATE 增加字段**：`ota_result` / `ota_stage`（如 `verify_fail`、`aborted`、`slot_written=false`），便于自动化断言，避免仅靠 `ok` 字段判断。
4. **补充“不写入”的直接证据**：OTA 前后读取 slot=b 头部哈希或全 `0xFF` 状态，断言未被擦写。
5. **复位后校验启动流程**：覆盖 bootloader 对 slot 的二次校验，验证“校验失败镜像永不启动”的端到端场景。

## 验收标准

- 修复后重跑 TC-05：日志出现 `verify fail reason=... abort`，`STATE.ok=False`，`STATE.ota_stage=aborted`。
- OTA 前后 slot=b 头部哈希不变（或保持全 `0xFF`），证明未发生擦写。
- 注入失效时可被用例自身断言显式识别（避免再次出现同类误判）。

## 影响范围

- 当前 TC-05 结论不可信（假失败，掩盖真实校验门控风险）。
- 若存在同类依赖镜像篡改注入的 OTA 负向用例，需一并排查注入逻辑。

技术构成

核心链路零第三方依赖，一个 Python 解释器就能跑；需要的能力都用适配器接出去。

Runtime

Python 3，标准库 urllib 直连模型，零第三方依赖。构建产物 23.3 KB，sha256 45a725fcceffd4fc

Model

DeepSeek deepseek-flash（OpenAI 兼容协议）。实测支持图像输入，所以文本与视觉可共用一个 Key；换成 vLLM / Ollama 只改环境变量。

Adapters

设备 sim-unpack（Mock / Sim / ADB / 串口）、构建 zip 或 docker、缺陷落本地 JSON 或 GitHub Issue。当前部署目标 mock-device-01。

Service

FastAPI webhook（/webhook/github、/runs），可选安装；纯 CLI 也能全流程跑。
